> Build this FIRST. API keys reference plans, so the plan documents must exist before keys are created.

---

### Step 2.1 — What This Collection Does

Stores the definition of each pricing tier — Free, Basic, Pro, Enterprise. Every API key inherits its rate limit rules from a plan (or overrides them individually).

---

### Step 2.2 — Schema

```
quota_plans
├── _id          ObjectId       Auto-generated by MongoDB
├── name         String         Plan tier name e.g. "Free", "Pro"
├── rules        Object
│   ├── requestsPerMinute  Int  Max requests allowed per minute window
│   ├── requestsPerDay     Int  Max requests allowed per day window
│   └── burstLimit         Int  Short spike allowance above per-minute limit
├── description  String         Human-readable description of the plan
└── active       Boolean        Whether this plan is currently offered
```

## PART 4 — COLLECTION: `api_keys`

---

### Step 4.1 — What This Collection Does

Stores every API key issued to developers. Each key is linked to a plan (for default rules) and optionally carries its own `quotaRules` override. When a key is revoked, `revokedAt` is set and `active` becomes false.

---

### Step 4.2 — Schema

```
api_keys
├── _id            ObjectId    Auto-generated
├── developerId    ObjectId    Reference → developers._id
├── keyHash        String      SHA-256 hash of the actual API key string
├── planId         ObjectId    Reference → quota_plans._id
├── active         Boolean     true = usable, false = revoked/expired
├── quotaRules     Object      Per-key overrides (if null, use plan rules)
│   ├── requestsPerMinute  Int
│   ├── requestsPerDay     Int
│   └── burstLimit         Int
├── createdAt      Date
└── revokedAt      Date | null  Set when key is revoked, null otherwise
```

> **Why keyHash and not the actual key?**
> The real key is shown to the developer only once at creation. The database only stores its hash (like a password). This is a standard security practice — even if the DB is compromised, keys cannot be recovered.

---

### Step 4.3 — Create Collection with Schema Validator

```javascript

        keyHash: {
          bsonType: "string",
          minLength: 32,
          description: "Must be a hash string of at least 32 characters"
        },
        planId: { bsonType: "objectId" },
        active: { bsonType: "bool" },
        quotaRules: {
          bsonType: ["object", "null"],
          properties: {
            requestsPerMinute: { bsonType: "int", minimum: 1 },
```

## PART 5 — COLLECTION: `usage_buckets`

---

### Step 5.1 — What This Collection Does

This is the core tracking collection. Every time an API key makes a request, the appropriate bucket document is **incremented by 1** using an atomic `$inc` + `upsert` operation. Three bucket types exist per key: `minute`, `hour`, and `day`. When checking if a key has exceeded its limit, you query the current bucket and compare `requestCount` to the plan's rule.

> **This pattern is called the Bucket Pattern** — one of MongoDB's official design patterns for high-frequency event data. Instead of inserting a new document per request (which creates millions of tiny docs), you group requests into time-window buckets and atomically increment a counter.

---

### Step 5.2 — Schema

```
usage_buckets
├── _id            ObjectId
├── apiKeyId       ObjectId    Reference → api_keys._id
├── developerId    ObjectId    Reference → developers._id
├── periodType     String      "minute" | "hour" | "day"
├── periodStart    Date        Start of this time window (floored to minute/hour/day)
├── requestCount   Int         Number of requests made in this window (incremented atomically)
└── lastUpdatedAt  Date        Timestamp of last increment
```

---

### Step 5.3 — Understanding periodStart (Time Window Flooring)

| periodType | Example periodStart           | Window covers               |
|------------|------------------------------|-----------------------------|
| `minute`   | 2024-03-15 **14:22**:00 UTC  | 14:22:00 → 14:22:59         |
| `hour`     | 2024-03-15 **14**:00:00 UTC  | 14:00:00 → 14:59:59         |
| `day`      | **2024-03-15** 00:00:00 UTC  | 00:00:00 → 23:59:59         |

---

### Step 5.4 — Create Collection with Schema Validator

```javascript
db.createCollection("usage_buckets", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["apiKeyId", "developerId", "periodType", "periodStart", "requestCount", "lastUpdatedAt"],
      properties: {
        apiKeyId:     { bsonType: "objectId" },
        developerId:  { bsonType: "objectId" },
        periodType: {
          bsonType: "string",
          enum: ["minute", "hour", "day"],
          description: "Must be minute, hour, or day"
        },
        periodStart:    { bsonType: "date" },
        requestCount: {
          bsonType: "int",
          minimum: 0
        },
        lastUpdatedAt:  { bsonType: "date" }
      }
    }
  },
  validationAction: "error"
});
```

---

### Step 5.5 — Create Indexes

```javascript
// The most critical index — used on every single API request
// Finds the current bucket for a key+period combination
db.usage_buckets.createIndex(
  { apiKeyId: 1, periodType: 1, periodStart: 1 },
  { unique: true }
);

// For developer-level rollup queries
db.usage_buckets.createIndex({ developerId: 1, periodType: 1, periodStart: 1 });

// For sorting/filtering by recency
db.usage_buckets.createIndex({ periodStart: -1 });

// TTL index: auto-delete minute buckets after 7 days (they pile up fast)
db.usage_buckets.createIndex(
  { periodStart: 1 },
  {
    expireAfterSeconds: 604800,       // 7 days = 7 × 24 × 3600
    partialFilterExpression: { periodType: "minute" },
    name: "ttl_minute_buckets_7days"
  }
);

// TTL index: auto-delete hour buckets after 90 days
db.usage_buckets.createIndex(
  { periodStart: 1 },
  {
    expireAfterSeconds: 7776000,      // 90 days
    partialFilterExpression: { periodType: "hour" },
    name: "ttl_hour_buckets_90days"
  }
);
```

---

### Step 5.6 — The Upsert Operation (Core Pattern)

This single operation is what runs every time a developer makes an API call. It either creates a new bucket for the current window, or increments the existing one — atomically.

```javascript
// Helper: floor a Date to the start of its period
function getPeriodStart(date, periodType) {
  const d = new Date(date);
  if (periodType === "minute") {
    d.setSeconds(0, 0);
  } else if (periodType === "hour") {
    d.setMinutes(0, 0, 0);
  } else if (periodType === "day") {
    d.setHours(0, 0, 0, 0);
  }
  return d;
}

// Core function: increment bucket for a given key + period
function incrementBucket(apiKeyId, developerId, periodType) {
  const now = new Date();
  const periodStart = getPeriodStart(now, periodType);

  db.usage_buckets.updateOne(
    {
      apiKeyId:    apiKeyId,
      periodType:  periodType,
      periodStart: periodStart
    },
    {
      $inc: { requestCount: 1 },
      $set: { lastUpdatedAt: now },
      $setOnInsert: {
        developerId: developerId
      }
    },
    { upsert: true }   // Create the document if it doesn't exist for this window
  );
}

// Usage: call this for all three period types on every request
// (so you always maintain a minute, hour, AND day counter)
const aliceKey = db.api_keys.findOne({
  developerId: db.developers.findOne({ email: "alice@techcorp.io" })._id,
  active: true
});

incrementBucket(aliceKey._id, aliceKey.developerId, "minute");
incrementBucket(aliceKey._id, aliceKey.developerId, "hour");
incrementBucket(aliceKey._id, aliceKey.developerId, "day");

print("Bucket incremented successfully");
```

```javascript
// The most important query in the entire project.
// Checks: has this key exceeded its per-minute, per-day, or burst limit?

function checkRateLimit(apiKeyId) {
  const now = new Date();

  // Floor to current minute and current day
  const minuteStart = new Date(now); minuteStart.setSeconds(0, 0);
  const dayStart    = new Date(now); dayStart.setHours(0, 0, 0, 0);

  // Step 1: Get the key document to know its effective rules
  const keyDoc = db.api_keys.findOne({ _id: apiKeyId, active: true });
  if (!keyDoc) return { allowed: false, reason: "Key not found or inactive" };

  // Step 2: Determine effective limits (override if key has its own quotaRules)
  let limits;
  if (keyDoc.quotaRules) {
    limits = keyDoc.quotaRules;
  } else {
    const plan = db.quota_plans.findOne({ _id: keyDoc.planId });
    limits = plan.rules;
  }

  // Step 3: Get current usage from buckets
  const minuteBucket = db.usage_buckets.findOne({
    apiKeyId:    apiKeyId,
    periodType:  "minute",
    periodStart: minuteStart
  });
  const dayBucket = db.usage_buckets.findOne({
    apiKeyId:    apiKeyId,
    periodType:  "day",
    periodStart: dayStart
  });

  const minuteUsage = minuteBucket ? minuteBucket.requestCount : 0;
  const dayUsage    = dayBucket    ? dayBucket.requestCount    : 0;

  // Step 4: Evaluate limits
  const withinMinute = minuteUsage < limits.requestsPerMinute;
  const withinBurst  = minuteUsage < (limits.requestsPerMinute + limits.burstLimit);
  const withinDay    = dayUsage    < limits.requestsPerDay;

  return {
    allowed: withinBurst && withinDay,
    minute: {
      used:  minuteUsage,
      limit: limits.requestsPerMinute,
      burst: limits.burstLimit,
      in_burst_zone: !withinMinute && withinBurst
    },
    day: {
      used:  dayUsage,
      limit: limits.requestsPerDay
    },
    evaluated_at: now
  };
}

// Test it
const aliceKey = db.api_keys.findOne({
  developerId: db.developers.findOne({ email: "alice@techcorp.io" })._id,
  active: true,
  quotaRules: null
});
printjson(checkRateLimit(aliceKey._id));
```

```javascript
db.developers.find({ status: "active" });

// Q5: Developers with no organization
db.developers.find({ organization: null });

// Q6: Developers registered in 2024
db.developers.find({
  createdAt: { $gte: new Date("2024-01-01"), $lt: new Date("2025-01-01") }
});

// ── API KEYS ─────────────────────────────────────────────────────────
// Q7: All active keys
db.api_keys.find({ active: true });

// Q8: All revoked keys
db.api_keys.find({ active: false, revokedAt: { $ne: null } });

// Q9: Keys that have custom quota overrides
db.api_keys.find({ quotaRules: { $ne: null } });

// Q10: All keys for Alice (join developer by email)
db.api_keys.find({
  developerId: db.developers.findOne({ email: "alice@techcorp.io" })._id
});

// ── USAGE BUCKETS ────────────────────────────────────────────────────
// Q11: Bob's total requests this week (aggregated daily buckets)
db.usage_buckets.aggregate([
  {
    $match: {
      apiKeyId:    db.api_keys.findOne({ developerId: db.developers.findOne({ email: "bob@startup.dev" })._id })._id,
      periodType:  "day",
      periodStart: { $gte: new Date("2024-03-09T00:00:00Z") }
    }
  },
  { $group: { _id: null, total: { $sum: "$requestCount" } } }
]);

// Q12: All hour buckets for Alice sorted ascending
db.usage_buckets.find({
  apiKeyId:   db.api_keys.findOne({ developerId: db.developers.findOne({ email: "alice@techcorp.io" })._id, active: true, quotaRules: null })._id,
  periodType: "hour"
}).sort({ periodStart: 1 });

// ── OVERAGE EVENTS ───────────────────────────────────────────────────
// Q13: All hard blocks (blocked actions)
db.overage_events.find({ actionTaken: "blocked" });

// Q14: All overage events for Bob
db.overage_events.find({
  developerId: db.developers.findOne({ email: "bob@startup.dev" })._id
}).sort({ time: -1 });

// Q15: Overage events in the last 30 days
db.overage_events.find({
  time: { $gte: new Date("2024-02-15T00:00:00Z") }
}).sort({ time: -1 });

// ── AUDIT LOGS ───────────────────────────────────────────────────────
// Q16: All actions performed by the billing system
db.audit_logs.find({ actorId: "billing-service" }).sort({ timestamp: -1 });

// Q17: Complete history of Alice's primary key
db.audit_logs.find({
  targetType: "api_key",
  targetId: db.api_keys.findOne({
    developerId: db.developers.findOne({ email: "alice@techcorp.io" })._id,
    active: true, quotaRules: null
  })._id.toString()
}).sort({ timestamp: -1 });

// Q18: All key revocation events
db.audit_logs.find({ action: "key.revoked" });
```
